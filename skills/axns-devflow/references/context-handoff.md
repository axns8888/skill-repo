# 上下文预算与执行窗口交接

在计划、阶段切换、准备读取大量材料或连续实施前，评估当前上下文能否承载下一单元。使用平台实际可见的剩余量、压缩提示、已加载材料规模，结合下一步输入/输出体量、依赖及恢复成本作判断。无法观测容量或剩余量时写“未知”，说明依据与不确定性；不得编造固定容量、剩余百分比、统一阈值或固定窗口数。出现压缩信号先核对唯一任务记录与实际工作区，避免从不完整记忆直接推进。

## 拆分有意义的执行单元

以能验证的调查结论、实施目标、复核范围或串行接续点划分窗口，不按每条 Todo 机械开窗。短小、连续且上下文可承载的修改可以留在当前窗口。阶段在逻辑上可独立并不等于已经允许派生代理；并行、平台选择、独立复核及先汇报等待均遵循用户现有授权。

确需拆分时，在原计划写清每个单元的：

- 目标及完成条件；需要按路径读取的输入。
- 可写 scope、共享文件修改权、依赖和可并行条件。
- 产出与验证方法；谁负责整合、组合验收及向用户汇报。
- 执行平台、当前执行者、交接点和下一动作。

协调窗口保留分工、状态、依赖及最小可验证摘要，引用任务记录和证据位置。实施细节、完整工具输出与大段日志留在对应工作单元，不反复回灌全部历史。调查/复核结果须指明检查范围、被检代码身份、结论及未覆盖处，摘要不能替代独立复核要求。

## 换窗前落盘、接续时按需恢复

使用现有唯一任务记录，通常为 `_plan/process/<task-id>/plan.md` 的当前状态区和已有交接文件；项目已有等价记录时沿用。不要另建第二份计划。切换前至少保存：

- task-id、当前目标、授权范围及用户限制，当前阶段。
- 唯一计划/当前状态/证据路径，已经完成与尚未完成的事。
- 实际 cwd、分支、HEAD、被验证的提交，未提交和未跟踪改动的位置与归属。
- 当前执行者、领取状态、scope/shared_claims，原执行者何时停止写入以及接续者如何核实接管。
- 仍有效的验证证据、失效原因、阻断项和下一条可执行动作。

不要复制整段聊天、无限日志、密钥或环境秘密。新窗口先核实登记、Git 事实与执行权，按需读取上述路径，再继续原阶段，不重做已经有有效证据的工作。已有授权持续有效，不因换窗再次要求相同确认。

## 上下文、执行权与 worktree 分别处理

同一未完成目标的串行接续保留原 task-id 与 worktree，不因换窗再创建嵌套工作区。旧窗口先停止写入，交接执行者；扩展领取中的阶段沿用其合法交接/回调协议，不复制领取 token 给两个执行者，也不清除登记来绕过互斥。

独立任务分别登记；启用 worktree 时使用各自工作区。并行单元须有不重叠写范围、依赖与整合责任，仅新开窗口不能获得写权限。同一任务的独立复核窗口可以只读检查同一提交，写入返修结论按既有记录与修改权约定处理。窗口可以复用，独立目标的任务目录不能无限续用。

## 工具不足或启动结果不明

按 [工具协作](tool-integration.md) 核实平台实际能力。缺少指定平台或独立上下文能力、达到嵌套深度或并行限制时，如实记录待执行的单元与能力缺口；可以继续已授权且不依赖它的工作。不得把当前窗口自查记成已完成指定平台/独立窗口复核。

启动请求无明确结果时，先查现有会话、任务登记和占用，再决定是否重试，不能连续重复派发。同一 task-id 不能因此出现两个写入者。无法启动就保留交接记录和待执行状态，不伪报成功，也不擅自突破用户的平台和等待要求。
