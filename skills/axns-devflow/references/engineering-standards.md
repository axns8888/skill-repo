# 工程规范建立与执行

本资料约束如何把完整系统的质量要求落到项目中，具体语言、框架和组件选择由项目决定。新建系统、快速创建项目、生成项目开发提示词时必须读取；既有项目只读取和补足本次涉及的规范，不进行无关整库治理。

## 交付深度与初始化出口

“快速创建”缩短准备时间，不降低已要求的系统交付深度。用户要求系统、应用或平台且未明确限定原型时，按实际可运行、可维护的系统安排本期范围；只有用户明确要求演示、原型或可行性探查，才采用对应边界，并标出尚未实现的部分。不自行加入未要求的业务模块、微服务或权限体系。

初始化脚本只复制文档。开始业务实现前，执行者还须根据需求与项目事实完成以下准备；已授权开发时直接完成，不新增审批环节：

1. 在项目基线记录交付深度、本期业务范围、真实用户入口及成功标准。大系统可分期，每期应形成可使用的业务闭环，不能把首页和空菜单当作一期完成。
2. 具体化架构规范：实际源码目录树、领域与层次、依赖方向、装配入口、数据和配置所有者，以及本期模块清单。明确提示词未点名的新增文件也按同一规则归属，不能全部堆入根目录或公共目录。
3. 具体化编码规范：命名对照表、注释规则、错误处理和契约规则；结合实际语言给出本项目文件、类型、函数、字段的例子。
4. 有界面时具体化 UI 规范：布局、组件复用、设计令牌、页面模式、反馈状态和视口验证；没有界面时在基线写明不适用，不生成业务 UI。
5. 以一个本期真实模块校准规范和实现：串起入口、处理、持久化或外部调用、回读及界面反馈（适用时），验证后再复用到其他模块。不能用断开内部连接的 mock 样板证明模块已完成。

技能附带的 [架构模板](../assets/architecture-baseline.md)、[编码模板](../assets/coding-baseline.md)、[UI 模板](../assets/ui-baseline.md) 会由初始化工具落到项目 prompts/；按事实填写项目决定，保留模板已有的通用底线。未决事项按影响处理：不影响当前工作可保留待核实，影响目录、公开契约或交互的决定应在对应代码前收敛。不得带着整份占位模板宣称规范建立完成。

## 项目规范的唯一入口

| 载体 | 具体责任 |
| --- | --- |
| 项目基线（默认 prompts/project.md） | 本期范围、交付深度、规范索引、模块清单、真实命令和完成状态 |
| prompts/architecture.md 或已有等价规范 | 源码树、模块边界、依赖、数据与配置归属、装配方式 |
| prompts/coding.md 或已有等价规范 | 术语、命名、注释、类型与错误处理约定 |
| prompts/ui.md 或已有等价规范 | 界面布局、设计令牌、公共组件、页面模式和状态 |
| 按需 module_<领域>.md | 本期领域的实体、用例、接口、状态、副作用、路径和验证入口 |
| guides/quality-gates.md 与任务记录 | 具体检查、证据、缺陷及交付判断 |

已有文档先判断现行入口；如项目已用新版基线替代 project.md，应复用现行文档，不因默认文件名恢复历史规则。只在已有 AGENTS.md 需要更新读取路径时有界维护；不覆盖用户规则，不靠安装技能让所有会话自动记住项目决定。

## 最低工程要求

| 维度 | 写代码前确定 | 实施与复核时核对 |
| --- | --- | --- |
| 源码组织 | 领域、层职责、准确落位、公开入口及允许依赖 | 所有新文件有归属；无平铺业务堆积、跨领域内部导入、重复公共能力或空壳分层 |
| 命名 | 领域词表、大小写、文件/类型/函数/字段规则及代表例 | 名称能说明职责和副作用；定义、导出、调用、动态引用及现行文档一致 |
| 注释 | 语言、需说明的边界与文档注释形式 | 领域模块/服务入口、公开契约、业务规则、复杂状态转换及异常恢复有必要说明；注释准确且随实现更新 |
| UI（适用时） | 公共布局、令牌、组件入口、页面与反馈模式 | 页面沿用同一规范；真实页面验证布局、交互和数据反馈，不能只检查 CSS 存在 |
| 业务闭环 | 输入、业务处理、状态、保存/调用、结果读取和错误反馈 | 可从真实入口完成目标；重启后数据保留等生命周期按实际需求验证 |
| 运行交付 | 启动方式、配置、依赖、必要数据初始化和排错入口 | 新环境能按说明运行；所需检查完成，缺失条件如实记录，不伪造可用状态 |

注释不是逐行翻译代码，也不按行数或覆盖率凑指标。对外可调用的业务服务和关键契约说明用途、输入/结果及必要副作用；状态机、重试、事务、单位、时间和外部限制解释业务原因；明显且无额外约束的局部访问器可省略。不能把“只解释复杂逻辑”执行成所有业务代码零注释。

## 本期系统完成矩阵

在现有任务计划或项目基线维护一次，不再复制一份进度台账。每个本期模块列出：用户入口与用例、源码位置、契约和数据所有者、依赖、应有的正常/异常状态、验证入口、当前缺口。适用时补充配置、数据初始化/迁移、资源释放、恢复与使用说明；不适用写明理由，不增造业务功能。

“已完成”应有真实实现和适用证据。演示数据、内存替代库、硬编码成功返回、空处理器、假按钮、关键 TODO、未接线菜单不能充作系统能力；测试夹具和显式授权的原型可以使用替代，并说明其范围。不得把本期必需闭环静默移入 future/。

## 各阶段如何消费规范

- 规划：读取现行规范，列准确文件路径和模块落位、公开命名、需补充的注释及 UI/数据状态；新增长期决定回写唯一规范。未指定目录的实现也按架构落位。
- 实施：先落实共用基础和一个真实模块，再按边界扩展；同步维护命名、注释、契约和文档。不要先生成大量平铺文件，最后再补规范。
- 自检与复核：按变更范围对照上表，结合差异、相邻模块和真实运行证据。命名变更检查旧符号/路径及动态引用；抽查关键业务注释；有 UI 时覆盖受影响页面状态和视口。无变化项可注明不适用。
- 交付：列明实现范围、规范检查、实际验证和缺口。技术门禁不受人工验收开关控制；本轮新增命名违例、应有注释缺失、目录越界、UI 不一致或必需闭环未完成，修正前不可宣称交付完成。不可执行的验证保留未验证结论，不制造通过。

小任务可以减少记录篇幅，仍遵守已有工程规范；完整系统任务不能借“小改动流程”豁免架构、业务闭环和必要验证。
