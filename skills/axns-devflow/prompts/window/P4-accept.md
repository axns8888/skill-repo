# P4 阶段 3：自动验收、合入与收尾

执行 axns-devflow 阶段 3。当前 task-id：{{task-id}}。读取 [人工验收配置](../../references/acceptance.md)，默认关闭。沿用用户对本任务的执行授权，连续完成验证、提交、本地合入、归档和任务资源删除；用户明确要求保留资源、仅评审或等待本次确认时尊重该要求。不要每一步重新询问。

**若 worktree 扩展启用**：

1. 读取共享登记，按 depends_on 顺序处理。依赖未 completed 时等待其正常收尾；共享文件任务按持权顺序串行。普通等待不升级给用户，独立任务继续。
2. 从任务 worktree 运行扩展 `commit --project <任务目录> --id <task-id> --message <摘要>`，脚本校验范围并提交。合并最新本地集成分支：`git merge --no-ff --no-commit <集成分支>`。冲突在任务分支自行分析和解决，保留双方必要行为；不盲选 ours/theirs，不在集成分支修冲突。
3. 对组合结果执行项目实际验收命令与必要语义复核。失败先诊断、修复、复验，有进展时继续；无进展时改变方案，避免机械重复。通过后用 commit 完成合并提交；已是最新且无变化时不造空提交。
4. 维护并提交本任务 `acceptance.md`，包含检查命令及真实结果、阻断项关闭证据、受测代码身份和技术结论，单独记录人工策略及状态。记录最终候选 HEAD；后续代码变更使原验收失效，按影响重新验证。仅显式 blocking 的人工验收等待该候选的真实确认。非阻塞人工待办进入台账，不冒充用户通过。
5. 按项目约定自行清理本次可再生缓存/依赖等 ignored 内容；有价值的本地内容先保留到主目录任务归档并核实，不能无差别强删。停止本任务后台进程，切换终端工作目录；PyCharm 如占用目录则先释放占用，仅确实无法处理时请求用户操作。
6. **普通会话**切到主检出目录运行 `finish --project <主目录> --id <task-id> --accepted-head <最终HEAD>`；已有真实人工确认时附 `--human-accepted-by <依据>`。finish 自动快进合入、先写归档，再删除本任务 worktree 和已合入本地分支，最后完成归档与释放持权。集成分支前移则返回任务分支重新组合验证；脏主工作区保留其内容，查明归属后处理，不替其他任务提交或 stash。
7. **autopilot 派发会话**不在自己的工作区内执行 finish。先完成以上验证和清理，再按工单 `complete --evidence acceptance.md --accepted-head <最终HEAD> --handoff`，有真实人工确认时附其依据，然后结束本轮。下一轮从主检出目录 `claim/tick` 自动执行 finish，也可由控制者调用 `runner.cjs finish`。重复清理使用同一 task-id 与 accepted-head；中途失败保留持权和恢复归档。

**若扩展未启用**：按宿主验收出口及已有授权完成交接/合入，更新 `_plan/.active_plan`，不创建扩展登记文件。

只有重大且无法在当前授权内安全解决的问题才使用 P5。次数、超时和普通 Git/测试失败本身不构成用户介入理由；任务授权不包含远程推送、发布或删除远程分支。

完成后一次回报技术检查、候选/集成提交、归档位置、worktree/本地分支删除结果及独立人工验收状态。未执行部分如实标记。结案或完成执行权交接后会话可接续新任务，但重新核实任务身份、目录、分支和授权。
