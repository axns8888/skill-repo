# P1 阶段 0：任务登记

仅新交付确需登记时创建任务；已派发的 P1 只核实并补齐既有登记。启用 worktree 不等于所有事项都要登记隔离，单纯状态、只读协作及无冲突的项目级维护走各自最小入口。确需隔离时从配置的集成分支冻结本批基线；平台已提供合法任务目录时先核实映射及持权，不嵌套复制工作区。

执行 axns-devflow 阶段 0。任务：{{任务描述}}。核实模式、已有授权及登记方案后直接执行已授权动作；只有缺少必要决定时才等待。普通小改动且未使用扩展登记时可直接按宿主轻量流程处理。

1. 已有 task-id 和有效登记时，核实并补齐原记录，保留现有工作目录和执行权，不另建任务或覆盖其他活动指针。同一任务跨阶段、返修和跨会话接续均复用原 worktree；新独立任务使用 `YYMMDD-类型序号-任务标题`（例如 `261117-A01-weknora-mcp-config`），复用项目 `_plan/prompts/task-types.json` 的类型，按日期与类型递增序号。无既有编码时默认 A 新增、M 修改、F 修复、R 复核；轻量任务已有编号无需迁移。启用 worktree 时可用 `register --type A --title weknora-mcp-config` 在共享锁内分配编号，不自行并发猜号。确认有界目标、交付物、成功标准、范围、依赖和整合责任，再执行适用登记。Worktree 必须在该任务首次业务代码修改前完成登记；扩展登记完成前不在主检出目录另建任务副本。
2. **若 worktree 扩展启用**，按扩展登记协议操作：在共享协调锁内，从已核实的集成分支创建 `.worktrees/<task-id>` 与 `task/<task-id>`，然后校验 scope、shared_claims、depends_on。scope 相交则拒绝登记并回滚本次新建资源；共享修改权冲突则登记为 blocked，保留任务窗口，不获得任何修改权。通过后写 parallel.json、共享活动指针及 `task.claimed` 事件。仅在新任务 worktree 的 `_plan/process/<task-id>/` 按宿主模板补足计划骨架，不提前宣称持权。
3. **若扩展未启用**，在当前项目 `_plan/process/<task-id>/` 建立计划骨架，写 `_plan/.active_plan` 指向本任务；不创建 worktree、active 目录或注册表。
4. worktree 模式登记后切换到任务 worktree；单任务模式继续使用当前项目目录。阻断任务恢复须重新仲裁，不能手改指针抢占。

并发窗口数不是 worktree 总数；已结案任务清理并释放窗口后，后续独立任务仍须新建自己的 worktree。自动调度仅处理已登记任务，不自动将 Todo 拆成任务或创建工作区。

持续需求收集要定义本批范围与停止条件；未来需求保留在台账，不能无限追加进同一工作区。拆分依据为可交付目标、依赖和验证成本，不按文件数、Todo 或窗口数设机械阈值。上下文不足时按 [上下文预算与交接](../../references/context-handoff.md) 保存交接，同一目标保留 task-id。

回报：task-id、模式、worktree 绝对路径、分支、scope / shared_claims / depends_on、校验结果与占用方、事件位置、计划入口、下一步。

扩展同时交付批次 1（创建/清理、登记、指针、事件）与批次 2（范围和修改权校验），检查会阻断。若目标环境使用仅批次 1 的旧扩展，必须报告“仅告警、不具备阻断保护”。
