# 通用开发工作流

将用户目标转成可执行计划、实际变更和可追溯验证。技术方案、工具、业务源码目录和命令由目标项目决定；新项目采用固定的最低流程目录骨架。默认用中文输出，跟随用户指定语言。

## 入口与范围

1. 区分本次是流程文档、方案、开发、复核、验收清单、结案，还是构建发布。只交付方案或提示词时，按请求交付文档。
2. 读取适用的 `AGENTS.md`、项目基线（默认 `_plan/prompts/project.md`）、本次任务涉及的项目规范、相关源码和任务记录，核实工具配置及实际命令。技术栈、架构、界面、接口与发布约定由项目基线和专题规范维护，不写成通用流程要求。已有项目沿用其技术选型、模块边界和约定；新项目只补足当前目标所需的决策。
3. 接续任务先恢复原目标、已有授权、唯一计划、实际变更和有效证据。用户已要求执行的范围持续推进；普通实现选择、阶段切换不重复请求同一授权。独立交接边界按用户要求保留，不自行派生代理。
4. 新项目启动或生成开发流程时，先读 [最低目录结构与初始化](references/project-layout.md)。流程至少包含 `_doc`、`_plan` 及规定子目录、README 和 `flow.md`；已授权落盘时用 `scripts/init-workflow.cjs` 或等价手工方式完整创建，已有项目只有在本次需要建立或补齐流程时才增量补齐，普通修改直接复用现有规范与记录。
5. 需要正式登记或跨会话接续时使用 [窗口提示词](prompts/window/P0-open.md)，从当前实际阶段进入 P0–P4，不补跑已完成阶段；P5 仅扩展启用时使用。默认单任务，正式登记时写 `_plan/.active_plan`。只有项目 AGENTS.md 的 `extensions` 包含 `worktree` 才加载 axns-devflow-ext-worktree 并使用其共享登记；安装或提及扩展不代表启用。P0 核实状态后沿用已有执行授权；只有用户明确要求先汇报等待，或缺少必要授权、关键决策时才等待。 若同一 AGENTS.md 的 `extensions` 还包含 `autopilot`，加载 axns-devflow-ext-autopilot 生成只读调度建议；阶段执行、开窗与模型选择仍受已有授权和平台能力约束，不因启用而自行派生代理。
6. 按任务规模裁剪：小改动可在一份记录或交付回复中说明目标、变更、验证与待办；跨模块、存在关键不确定性或需要多轮交接时，再建立正式计划、证据及复核记录。已有等价载体直接复用。普通小改动不要求初始化目录、填写整份模板或写活动指针；已纳入 autopilot/worktree 的任务仍保留领取、持权、证据和回调协议，记录正文可以精简。

人工验收由项目 `_plan/prompts/acceptance.json` 独立控制，默认关闭。开启后默认单独跟踪，不阻塞自动执行；仅显式 `blocking: true` 才在当前任务最终合入、结案前等待确认。技术门禁和既有授权继续生效，详见 [人工验收配置](references/acceptance.md)。

## 核心原则

- **服务用户的工作**：用户明确的任务范围、流程选择和已有授权优先于本技能的默认组织方式。按实际需要选择阶段、工具和记录，不因使用技能增加重复确认、重复清单或范围外工作；真实结果、已有工作和当前执行权仍须核实。

- **项目事实决定实现**：先核实入口、配置、依赖、契约和既有模式，再形成方案。不从本 skill 推导语言、框架、分层、通信、存储、界面或批量处理策略。
- **目标与证据闭合**：成功标准描述触发条件与可观察结果；复杂任务用稳定 R 编号关联执行证据 E。检查覆盖本次关键内部边界，明确替代依赖与未覆盖部分。
- **计划与结论各有唯一入口**：实质范围、方案、契约或验证方法变更才更新计划版本；状态与进度不另建竞争计划。
- **保护已有工作**：记录开始时未提交及未跟踪变更，限定本次写入范围，保留无关工作；共享记录做有界增量编辑。
- **验证与风险相称**：采用项目要求和本次变化所需的检查；文档变更查内容、引用和格式，逻辑变更查相关行为。构建是否必要由受改内容和项目门禁决定，打包、部署与发布按实际任务接入。
- **状态如实分开**：已实现、自动验证、交验资格、用户验收、结案分别记录。未执行、环境缺失、历史通过和当前通过不能混写。
- **流程不扩张授权**：计划、复核和结案不自动授权外部发布、数据处置或现场清理。已有授权按其范围继续有效，不增设固定审批点。启用 worktree 后，已授权任务的范围内提交、本地合入、归档及本任务工作区/分支清理由扩展自动闭环，明确的用户限制仍优先。

## 执行流程

### 1. 恢复事实并定义成功标准

新项目先落实最低目录骨架：`_doc/README.md` 为资料入口，`_plan/README.md` 为流程入口，`_plan/flow.md` 串联阶段，基线与提示词放 `prompts/`，任务放 `process/`，台账放 `ledger/`，延期项放 `future/`。只交付流程方案时也要写明完整结构及初始化方法。

明确目标、成功标准、非目标、当前阶段、已有授权和工作区基线。区分可自行核查的事实、可暂用且需注明的假设、真正阻断的决策；先推进不受阻的部分。

从实际入口追踪到处理、结果及适用副作用，只描述项目存在的环节。涉及状态、配置、资源或外部依赖时，明确所有者、生命周期与验证边界。

### 2. 形成计划并实施

按依赖顺序列出必要变更、复用点、受影响契约和验证方法。按需评估复杂度与不确定性；高不确定项先做有明确出口的探查，不一次搭建所有基础设施。

缺陷保留失败输入、预期与实际结果，定位根因后修复。实现过程中核对变更是否仍满足成功标准，更新受影响计划与记录。

### 3. 自检、复核与交接

执行适用检查，记录实际命令或操作、环境、退出码、业务断言、受测版本和未覆盖边界。修复本轮新增问题及阻断本次目标的旧问题，复用仍有效的证据。

纯复核按既定范围判断实现及证据，发现需修复的问题形成具体交接；用户已要求复核并修复时完成两个阶段并分别记录。交付实际变更、验证摘要、未关闭项及下一动作。

### 4. 验收与回流

项目或用户需要人工验收时，提供有前置、操作和可观察预期的清单；只按用户明确确认的日期、受测版本及范围记录通过，部分通过分别处理。自动验证不代替用户确认。

按项目要求更新现行基线、验收依据和任务索引。人工确认与自动检查的关系遵从项目规则，保留真实执行历史；不得据此绕过强制门禁。人工验收关闭或非阻塞时按技术交付标准及已有授权结案；非阻塞待确认项保留台账入口，关闭时不生成空人工验收流程。

## 提示词交付

需要阶段指令时，从提示词集裁剪并替换已知任务号、路径、阶段和版本，只有缺失输入保留 `〈变量〉`。每条完整指令单独使用 `text` 围栏代码块，说明和状态放在块外。只提供当前需要的交接，不要求用户重新执行已完成阶段。
