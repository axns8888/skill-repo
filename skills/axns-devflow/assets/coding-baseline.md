# 〈项目名称〉编码、命名与注释规范

首次实现前填好本项目决定，已有规范优先。本规范适用于提示词未逐个列出的全部新增实现，也用于本次修改涉及的代码。

## 项目决定与命名表

- 注释/文档语言：默认中文，按团队或用户要求调整；源码统一 UTF-8，遵循已有格式工具。
- 各语言的格式、静态检查、类型检查及实际运行命令：〈核实工具和配置后填入〉
- 允许缩写及同名异义的区分：〈例如本项目采用 config/env/repo 或完整拼写，选定后统一〉

| 对象 | 本项目规则 | 一个真实名称与路径/含义 |
| --- | --- | --- |
| 领域、目录与实现文件 | 〈语言/框架要求、大小写和领域辨识方式〉 | 〈例子〉 |
| 类型、组件、模型 | 〈大小写、领域与职责规则〉 | 〈例子〉 |
| 函数、方法与事件 | 〈动词、对象及事件形式〉 | 〈例子〉 |
| 变量、布尔值、常量 | 〈单位、复数、布尔前缀和常量形式〉 | 〈例子〉 |
| API/数据字段、枚举与配置 | 〈字段风格、边界转换与唯一来源〉 | 〈例子〉 |

同一业务概念使用同一词根。遵循语言和框架约定，不对外部协议/已发布契约机械改名。文件名结合所属目录能辨认职责；是否需要领域前缀由项目决定，禁止无意义地叠加前缀。

## 命名与调用语义

- 名称体现业务对象与职责，不随意使用 data、item、temp、manager、helper、utils 包办整片业务。短循环变量和上下文清楚的局部值无需机械长命名。
- 函数使用语言惯例下的“动词 + 对象”；读取、生成、保存、校验、解析、补齐缓存分别表达，带写入或网络等副作用的操作不能伪装成纯读取。布尔值表达可直接判断的含义，数量、金额、时长明确单位和精度。
- 类型与返回值语义一致：单值、列表、分页、聚合结果、可空与错误明确；不得同名函数在不同模块各表示不同业务动作。
- 写代码前确定新文件、公开类型和方法名称；重命名列旧→新映射并同步定义、导出、导入、调用、动态字符串、测试和现行说明。交付检查残留名称及保留依据，不把编译成功当作命名合规。

## 注释与文档注释

- 领域模块和业务服务入口说明职责、边界及关键依赖；用途已由框架明确的短入口可简写，不为每个文件复制模板头。
- 公开业务函数、服务方法和关键数据契约按语言惯例写文档注释，说明业务用途；参数/返回值中不直观的单位、空值、错误、副作用与资源责任按实际补充。不要重复类型签名已说清的内容。
- 业务规则、复杂算法、状态转换、并发/重试/取消、事务边界、兼容处理及外部协议限制，在相应实现附近说明“为什么这样做”和必要不变量，不能只写“处理数据”。
- 修复非直观问题时保留其触发条件或设计原因；不写聊天记录、作者流水账或已失效的方案。改实现同步改注释，保留仍准确的既有说明。
- 简单赋值、直接访问器和明显局部逻辑可不注释；不追求逐行注释或固定注释比例，也不能交付关键业务无任何说明的代码。
- 关键功能不得以 TODO、pass、空处理器、伪造成功或“其余代码不变”充作实现。合法的协议空方法、测试替代或明确延期项说明原因和范围。

## 实现边界

- 公共契约和业务边界采用技术栈适用的类型/模型；输入、输出、状态、错误与副作用有确定含义，内部与外部字段转换集中处理。
- 错误应可定位并反馈给调用方；不吞异常、静默跳过必要步骤或把失败返回成功。重试、超时、取消、幂等与资源释放按本期实际场景设计。
- 数据访问、参数化查询、事务与迁移归到明确所有者；界面不绕过领域 API，业务层不随意读写他域内部状态。配置、字典和常量复用唯一来源。
- 优先使用既有公共能力和锁定依赖，不编造 API 或字段；必要时核实官方资料。格式和检查工具沿用项目，不以修复局部问题为由全库格式化。

## 本期复核
