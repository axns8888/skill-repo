下面是按 `axns-devflow` + `axns-devflow-ext-worktree` 命名、批次顺序对调后的完整提示词。结构不变，只改命名、开关判断和批次表述，可直接贴进 AI 编码对话窗口。

---

## 使用方式

- 一个对话窗口 = 一个任务窗口。开窗先贴 **P0**，之后按阶段贴 P1–P4。
- `{{...}}` 是占位符，粘贴前替换成实际值。
- worktree 扩展未启用时，P0 走单任务分支，后续带“若 worktree 扩展启用”的段落可忽略。
- 每段都要求 AI **先回报判定再动手**，便于你在窗口里确认它读对了项目约定。
- **P5 仅 worktree 扩展启用时使用**，未启用不贴。

## P0 开窗提示词（每个任务窗口第一条，必贴）

```text
你是 axns-devflow 的执行代理，当前对话窗口绑定一个任务。先读项目现状，再开始任何动作。

【读取顺序，逐项确认后再往下】
1. 项目约定：AGENTS.md
2. 项目基线：prompts/project.md
3. 活动任务：_plan/active/ 目录；若不存在，读 _plan/.active_plan
4. worktree 扩展是否启用：看 AGENTS.md 是否声明 extensions 包含 worktree
5. 当前工作区差异：git status 与 git diff

【读完先回报，不要动手】
- 是否启用 worktree 扩展：是/否
- 当前活动任务列表（task-id 及状态）
- 本窗口要执行的任务：{{任务描述}}
- 你判断本任务应走的模式：单任务 / worktree 隔离
- 若启用扩展：本任务 scope、shared_claims、depends_on 的初步判断

【不变量，全程遵守】
1. 任务实际位于 process/<任务号>/，计划、证据、当前结论在同一任务目录内维护。
2. 证据必须来自实际执行（命令输出、测试结果、diff），不得推测填写。
3. 复核结论区分阻断项与建议项；阻断项未关闭不得进入验收。
4. 验收通过前不得合入集成分支；不得在集成分支上直接解决冲突。
5. 若 worktree 扩展启用：每个任务绑定独立 worktree 与分支；两个任务 scope 不允许交集；同一共享文件同一时刻只允许一个任务持有修改权；提交信息以 <task-id>: 开头。
6. 不确定时明确说“需要确认”，不猜测项目约定。

回报完等我确认，再进入阶段 0。
```

## P1 阶段 0：任务登记

```text
执行 axns-devflow 阶段 0：任务登记。任务：{{任务描述}}

步骤：
1. 分配 task-id（日期前缀 + 短标识），在 process/<任务号>/ 创建任务目录，按宿主模板写计划骨架。
2. 若 worktree 扩展启用：
   a. 写 parallel.json：scope、shared_claims、depends_on、owner、base_commit。
   b. 检查 scope 是否与现有活动任务有交集；有交集则拒绝登记，说明冲突任务。
   c. 检查 shared_claims 是否与其他活动任务的锁冲突；冲突则任务置 blocked，说明占用方，停止。
   d. 校验通过后创建 worktree（.worktrees/<task-id>）与分支（task/<task-id>），写 _plan/active/<task-id>.pointer，追加 task.claimed 事件到 registry.jsonl。
3. 若 worktree 扩展未启用：写 _plan/.active_plan 单指针，不创建 worktree、不写注册表。
4. 输出登记结果。

输出（按此格式回报）：
- task-id：
- 模式：单任务 / worktree 隔离
- worktree 路径（扩展启用时）：
- 分支名（扩展启用时）：
- scope / shared_claims / depends_on：
- scope 与锁校验结果：
- 事件记录位置（扩展启用时）：
- 计划骨架路径：
- 下一步建议：
```

> 批次说明：此阶段对应扩展批次 1（worktree 创建/清理 + 登记 + 指针 + 事件）与批次 2（锁与 scope 校验）。若扩展只交付了批次 1，步骤 2b/2c 标注为“暂走告警，不阻断”，并在回报里注明。

## P2 阶段 1：执行

```text
执行 axns-devflow 阶段 1：任务执行。当前 task-id：{{task-id}}

步骤：
1. 在任务 worktree（单任务模式则为当前工作目录）内推进计划，每步产出证据并写入任务目录。
2. 每次提交前自检：
   - worktree 扩展启用时：diff 是否全部落在 scope 内？涉及的共享文件是否由本任务持有修改权？
   - 不满足则阻断提交，说明越界文件或冲突文件，等我处理。
3. 提交信息以 <task-id>: 开头。
4. 需要修改 scope 外文件或未持有修改权的共享文件：停下来发起范围变更，说明要改什么、为什么、影响哪个任务，等我确认，不得直接改。
5. 每完成一个可验证步骤就回报，不要攒到最后一次性汇报。

输出（每步回报）：
- 本步做了什么：
- 证据位置（文件路径 / 命令输出摘要）：
- 提交哈希：
- 自检结论：通过 / 阻断（阻断时说明原因）
- 计划剩余项：
```

## P3 阶段 2：复核

```text
执行 axns-devflow 阶段 2：复核。当前 task-id：{{task-id}}

步骤：
1. 运行宿主既有复核项，结论分为阻断项与建议项。
2. worktree 扩展启用时，追加并行阻断项：
   - 隔离检查：本任务改动是否全部发生在自己的 worktree 与分支内
   - 越界检查：diff 是否全部在 scope 内
   - 锁合规检查：改动涉及的共享文件是否由本任务持有修改权
   - 语义冲突检查：接口调用方是否同步更新、测试夹具是否影响其他任务、依赖锁文件是否兼容
3. 每条阻断项必须给出关闭条件；建议项给出明确结论（改或不改及理由）。
4. 任一阻断项未关闭，不得进入验收。

输出（按此格式回报）：
- 阻断项清单：编号 / 描述 / 关闭条件 / 责任人
- 建议项清单：编号 / 描述 / 结论
- 复核结论：通过 / 阻断（阻断时列出未关闭项编号）
- 下一步建议：
```

## P4 阶段 3：验收与合入

```text
执行 axns-devflow 阶段 3：验收与合入。当前 task-id：{{task-id}}

前置确认（不满足则停止并说明）：
- 阶段 2 阻断项全部关闭
- 验收标准中的检查项全部通过

步骤：
1. worktree 扩展启用时，在任务 worktree 内执行 git merge --no-commit {{集成分支}}：
   - 有文本冲突 → 阻断，回阶段 1 处理，不得在集成分支上解决
   - 无冲突 → 跑语义检查清单与该任务验收检查项
2. 合入：按 depends_on 拓扑排序；同共享文件的任务严格串行合入。
3. 合入后（扩展启用时）：追加 task.completed 事件，释放 shared_claims 修改权，指针移入 _plan/archive/，执行 git worktree remove 清理工作区，分支保留至迭代结束。
4. 单任务模式：直接按宿主验收出口合入，更新 .active_plan。
5. 全程不得跳过合并验证直接合入。

输出（按此格式回报）：
- 合并验证结果：无冲突 / 有冲突（列出文件）
- 语义检查结论：
- 合入顺序与依据：
- 修改权释放记录（扩展启用时）：
- 归档位置：
- worktree 清理结果（扩展启用时）：
- 任务最终状态：
```

## P5 阶段 4：升级协调（仅 worktree 扩展启用时使用）

```text
执行 axns-devflow 阶段 4：升级协调。当前 task-id：{{task-id}}

先判定是否满足触发条件（任一满足即暂停任务）：
- 同一任务 rebase 后出现两次相同冲突
- 两个任务提出互不兼容的修改方案
- 某任务连续两次因同一 CI 检查失败且原因涉及共享文件
- 共享文件修改权等待超过 lock_timeout_minutes（读扩展配置，默认 120 分钟）

动作：
1. 暂停该任务，不再推进。
2. 记录 task.escalated 事件到 registry.jsonl。
3. 向我说明：冲突双方任务、已尝试的方案、需要裁决的点。
4. 不得自行放宽隔离与冲突预防规则、不得自行调整 scope 或拆分规则。

输出（按此格式回报）：
- 触发条件：
- 涉及任务：
- 已尝试方案：
- 待裁决事项：
- 建议裁决选项（只列选项，不替我做决定）：
```

## 窗口侧两个配套约定

**1. 窗口与任务一一对应，不复用。** 任务验收关闭后该窗口不再接新任务；新任务开新窗口贴 P0。这样 `_plan/active/` 指针、修改权持有关系、事件流都能和窗口生命周期对齐。

**2. 跨窗口只通过文件通信，不通过对话。** 依赖判断读 `_plan/active/` 与 `registry.jsonl`，不在两个窗口间手工传话。这也是 P0 要求先回报活动任务列表的原因。

## skill 目录结构

```
axns-devflow/
  prompts/
    window/
      P0-open.md
      P1-register.md
      P2-execute.md
      P3-review.md
      P4-accept.md
      P5-escalate.md      # 仅 ext-worktree 启用时使用
```

P1–P5 是宿主与扩展共用一套，靠“若 worktree 扩展启用”分支区分，窗口侧不维护两套。P5 标注为扩展专属，未启用不贴。

## 相比上一版的变化清单

| 项          | 上一版                     | 本版                                           |
|-------------|----------------------------|------------------------------------------------|
| 扩展名      | `ext-parallel`             | `ext-worktree`                                 |
| 开关判断    | `extensions` 含 `parallel` | `extensions` 含 `worktree`                     |
| 模式名      | 单任务 / 并行              | 单任务 / worktree 隔离                         |
| 批次顺序    | 锁协议在前，worktree 在后  | worktree 登记在前，锁与 scope 校验在后         |
| P1 步骤     | 先仲裁锁再建 worktree      | 先建 worktree 再校验 scope/锁                  |
| P3 复核项   | 越界、锁、语义             | 增加“隔离检查”（改动是否都在自己 worktree 内） |
| P4 清理     | worktree remove            | 不变，明确分支保留至迭代结束                   |
| P5 触发条件 | 锁等待超时                 | 改为“共享文件修改权等待超时”，与扩展命名对齐   |
