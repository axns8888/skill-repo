## 用户反馈与最新澄清

### 使用者报告，尚未现场核验

1. 一台主机持续运行，当前使用 master 工作目录及 admin-contracts、knowledge-lifecycle 两个 worktree；使用者认为复杂度增加，没有感受到效率提升。
2. admin-contracts 工作区干净，没有 master 未包含的提交；需确认任务记录和本地文件保全后才能退役。
3. knowledge-lifecycle 没有独有提交，master 多一个全局模型配置提交，但任务工作区仍有未提交业务代码、测试和记录，需先保全再从当前基线接续原任务。
4. 两个工作区没有形成独立交付线，增加持权、同步和收尾成本；此前全局模型配置进入业务 worktree，被使用者指出归属不合适。
5. 使用者建议保留计划、验证和模型选择；迁移必须沿用原任务和计划，不能把工作区收拢当成业务验收通过。

以上是使用者报告，本轮未进入 SmartKnora 仓库独立核实。原报告中的 master 仅表示当时项目状态。

### 用户最新要求

1. 主协调入口集中管理全局计划与调度；worktree 是明确交付目标的执行工作区，完成验收合入后退役，不能持续演变为新的总控。
2. worktree 可以用于单个功能，也可以承载同一交付目标下的一条有限任务链；不按每个步骤、模型或窗口分别建分支。
3. 主协调入口不绑定 master，也不绑定 main。后续项目或批次可以选择其他分支，须区分协调角色、控制目录、集成分支、任务分支。
4. 检查其他技能的关联影响，明确需要同步调整的范围。
5. 用户观察大部分 token 消耗在频繁读取交互，实际工作产出约 10%。该比例未经日志统计核验，不作为测量结论；需要检查重复读取、过细交接和多层派发开销。

本次澄清修正此前偏重“收回单工作区”的解释：候选方向为集中调度、临时执行工作区、按交付划分任务、减少无效交互。单工作区串行执行保留为轻量路径，不将取消 worktree 当成统一目标。

## 分支、目录、角色与执行单元

| 概念 | 候选职责 | 生命周期与约束 |
| --- | --- | --- |
| 主协调者 | 维护全局目标、权威计划、依赖、派发和整合决定 | 可以由不同会话接续；不要求永久在线的模型或固定分支名 |
| 共享控制目录 | 保存项目协调状态、索引与适用配置 | 位置需显式可定位；不能根据目录当前分支推断协调权限 |
| 集成分支 | 承接本批交付的目标分支 | 使用项目实际配置；派发时记录目标和基线，不能悄悄随当前检出分支改变 |
| 任务 worktree | 保存一次功能或有限任务链的代码与验证现场 | 换执行者沿用原任务；完整交付验收合入后退役 |
| 子代理或执行会话 | 执行一次有界委派 | 明确 cwd、任务身份、范围和回报；可在指定 worktree 中执行，不另立项目总计划 |

worktree 解决代码现场隔离，子代理解决执行与上下文分工；可以组合。执行者可在已授权目标内细化实现、排错和测试步骤；目标、范围、跨任务依赖及验收标准的实质变化交回主协调者处理。不要固定增加一层 worktree 总管；确需局部并行时明确授权范围和整合责任。

### 候选优化

- 同一会话首次进入读取必要指令、任务和相关源码；身份、指令或任务版本未变时复用已加载内容。新增范围、文件变化、外部写入、接管、压缩恢复或证据失效时，只重读对应材料。每个新执行会话仍核实适用指令，不能用缓存绕过现行授权。
- 派发包携带有界目标、权威计划引用、目标分支及基线、必要输入路径、写入范围、验收与停止条件；执行者从明确输入开始工作，避免再次全项目调查和重新制定总计划。
- 连续且上下文能承载的任务链复用执行会话；在真实预算、隔离、角色切换或独立复核要求触发时换窗。适用的模型路由与用户选择边界仍需遵守，不为省 token 擅自换模型或取消独立复核。
- 把必要身份、范围、持权及代码快照校验交给既有脚本；回传通过/阻断及变化摘要，异常时展开证据。保留提交和合入前的必要检查，不能笼统减少 heartbeat 或绕过执行预算；若要合并检查，先验证其生命周期语义。
- 查询先用 rg 定位，再读相关片段；对比已读内容的变化，避免反复整文件读取或因输出截断反复重读。已经存在的按需读取规则应落实到生成提示和请求数据。
- 状态不变的等待和轮询由平台/脚本处理；只在可执行、状态变化或需要决定时唤醒模型。进度反馈按实质进展和平台要求提供，详细日志和逐步清单留在证据文件，减少无变化的完整复述。
- 计划、执行清单和证据各有职责：只维护一份权威计划，状态变化集中更新；本地执行步骤不再复制一套项目计划，也不为普通实现细节启动新一轮登记、评审或确认。

### 验收与测量

选同一类真实任务对比调整前后：记录完成质量、验证覆盖、总耗时、会话/派发次数、重复读取次数、回传模型的输入量以及可获得的真实 token usage。将首次必要读取、重复读取、交接调度、实施、验证和返工分开；不把所有阅读或测试都视为无产出。

平台不提供 token 分类时，可用文件重复读取和回传文本量作代理指标，必须标注为估计，不能将字符数当 token。不得凭“10%”直接承诺节省比例，也不为测量额外开启全量会话回放或无关日志采集。

## 候选验收场景

| 场景 | 预期与可观察结果 |
| --- | --- |
| 项目选择 main、develop 或 release/某批次作为集成分支 | 所有派发、验证与合入使用实际配置和已记录的提交身份，不要求名为 master 的分支；协调入口角色不随分支名变化 |
| 执行中有人修改集成目标 | 明确检测并协调迁移，不悄悄把旧验收结果用于新目标；同批多目标能力单独评审 |
| 单功能或同一目标的有限任务链 | 目标、范围和结束条件明确；链内可接续执行者，完成完整交付后验收合入退役，不无限追加独立新目标 |
| 子代理或平台已有隔离目录 | 核实任务、目录和派发身份后复用或适配；不为同一次派发嵌套创建工作区，不产生第二套项目调度循环 |
| 同一会话连续修改、任务与规范未变化 | 按已知目标推进实现及必要验证；无需再次全量读取基线或重定计划，持权和提交校验仍有效 |
| 文件变化、接管或上下文恢复 | 重新核实相关身份与失效材料，使用已有有界摘要；不能把旧缓存或旧会话回执当作当前写入权 |
| 原工作区包含未提交业务代码、本地文件和原计划 | 保全并整合后接续原任务，核对写入者已停止，确认保全与接续结果后退役；不将迁移标为业务验收完成 |
| 无工作区隔离的串行调度 | 明确当前收尾能力差异；若批准补齐自动结案，保留真实验证和适用人工验收，主工作区不纳入删除逻辑 |

新增事实来源为用户指定的[减少重复读取与流程交互](../../../_skill进化树/axns-devflow/261121-减少重复读取与流程交互.md)，保留其原文与已暂存状态。本节整合该反馈和此前工作区职责澄清，作为后续实施的统一方案，不再新建平行需求或派发协议。

新反馈所述 9457de2、78 项隔离回归通过和 Admin 构建失败是来源会话的报告。本机缺少其 SmartKnora worktree 证据文件，本轮未验证该提交或测试；源反馈指向退役工作区的链接不作为本仓库可用证据，后续由原项目依据候选恢复核验。

### 1. 先按操作意图选入口，再判断需要哪些能力

extensions 表示项目允许使用的能力；具体操作仍需分类。已登记业务任务继续遵守原执行权与回调，不因轻量入口绕过现有保护。

| 操作意图 | 采用的最小动作 | 不额外触发的流程 |
| --- | --- | --- |
| 状态查询、只读诊断 | 窄读当前 Git/运行态及必要证据，直接回报事实 | 不初始化任务、不重跑构建、不重新选模、不加载历史长计划 |
| 项目级文档或配置维护 | 核实实际所有者与生效路径，检查写入冲突，执行本次有限变更 | 不扩大无关业务 scope，不因已启用扩展而创建业务 worktree |
| 既有任务接续 | 读取派发/接续摘要，核实失效材料与当前执行权，继续原目标 | 不重新登记、复制总计划或重做已经有效的步骤 |
| 新交付或有限任务链 | 主协调者明确目标、依赖、必要隔离及验收要求后派发 | 不按模型数、窗口数、Todo 数机械创建分支 |
| 快照保全或工作区收拢 | 明确保存、迁移或合入的实际目标，核对并保全所有需保留材料 | 不把保全自动解释为技术验收、部署或结案 |
| 技术交付 | 按被检代码身份执行适用验证、组合检查和合入门禁 | 不因用户希望减少开销而放行未通过的交付 |

新执行会话、模型路由改变或需要用户尚未选择的模型场景时，才进入对应路由决策；继续遵守现有“以生效表为准、已有明确选择可沿用”的约定。状态查询不因此召唤新模型。模型表缺失时一次说明来源与缺项，提供初始化或引用现有表的选择；不得用局部子代理发现结果拼成所谓完整目录。

### 2. 集中决策，复用现有工单与记录

主协调入口维护总目标、依赖、派发、整合与收尾决定，可在任意项目实际分支环境中运行，不以 master/main 判断权限。派发冻结本次目标分支和基线，后续配置变化显式处理。

优先保留现有目录和字段：总计划索引任务；任务 `_plan/process/<task-id>/` 保存经批准的执行目标、步骤状态与证据。执行者可更新实现步骤和事实，不能自行改写全局目标、增派独立任务或延长工作区寿命。无需先整体迁移所有计划文件，也不在每个 worktree 复制一份总计划；任务记录的物理位置不赋予项目级决策权。

复用现有 request/work_unit 的 task-id、cwd、HEAD、写入范围、inputs、route、callbacks 和证据路径，补齐必要权威计划/配置引用；不再新增一套工单、总控或运行台账。已派发执行者读取适用指令及本工单必要材料后实施，不重复执行协调者已完成的全项目调查、登记和选模。

一个工单允许覆盖上下文可承载的有限任务链，链内步骤不机械拆成新工单。换会话只由预算、角色/隔离或独立复核等真实条件触发；已有 yield/handoff 仍是旧执行者最后一次写入，不能为了复用会话在交权后继续修改。先调整工单粒度和入口提示，不先扩造同窗多派发引擎。

worktree 仅承载需要独立代码现场的交付；子代理在指定 cwd 执行。工具已有合法隔离目录时映射复用，避免同一任务重复建工作区。交付后由协调入口按真实验证决定合入和退役。

### 3. 给同窗事实定义失效条件，工具默认提供窄视图

| 已核实事实 | 可以复用的范围 | 重新核实的触发条件 |
| --- | --- | --- |
| task-id、cwd、目标分支、用户授权 | 同一会话、同一授权目标 | 接管、分支/目录或任务变化、用户新要求、上下文丢失 |
| HEAD、源码/配置状态、验证证据 | 对应的代码与环境身份未变化 | 提交、未提交改动、基线前移、相关配置/环境变化或外部写入；不能只看 HEAD |
| scope、持权和 dispatch | 解释性材料在本派发内复用 | 执行权变化、恢复、范围变化；实时校验仍由既有脚本在规定节点执行 |
| 模型来源、preset、scenario 和已确认路由 | 来源与选择未变化，且适用于当前动作 | 实际源文件/引用变化、新选择或新派发；已有会话不因改表自动换模型 |

先使用现有 brief/resume-brief 恢复能力，不新建摘要系统。缓存作用于已读文本和解释，不替代实时身份、持权、提交与合入前的检查。

面向模型的默认摘要只包括身份、状态、阻断/首个有效错误、下一动作、必要统计和证据路径；scope、候选模型目录和日志按实际需要展开。必要的用户选模仍展示来自权威表的相关完整选项，不能以节省输出隐藏可选项。

worktree status、模型查询及 runner 的现有完整 JSON 接口保持兼容，增加可选窄视图或在适配层提取摘要；自动化消费者不因默认结构变化受损。脚本本地处理完整数据，模型不接收整份 scope、917 行计划或完整 before/after。编辑后返回语义变更摘要与必要 diff，避免编码/行尾变化掩盖实际修改。

### 4. 项目级配置按实际所有者维护

先解析用户指定或项目实际引用的配置文件，区分个人共享表、项目表和任务专属文件；主目录不自动等于全部配置的所有者。项目统一模型表在权威位置维护，执行任务仅引用或读取，不因编辑器当前 cwd 在业务 worktree 就把配置归入该业务 scope。

项目级配置写入也必须检查活动任务的修改权和配置版本；优先复用协调锁及既有校验。若现有 helper 只支持任务 worktree，应补明确的项目维护适配，不能靠一句“配置例外”跳过并发保护。发生冲突则等待或交接，不能撤销其他业务任务持权。

受版本控制的配置变更独立检查和提交，不混入业务候选；控制目录已有无关未提交变更时保留现场并协调处理，不自动挪走它们。配置维护结束后，确保后续合入要求的工作区状态成立；生效引用应指向已确认文件，新路由只作用于适用的新派发。

### 5. 分类处理失败和等待

- 参数或格式错误：先核对接口并修正输入，相同输入与前提不变时不重复调用。
- hold、依赖未完成、持权冲突、相同配置缺项：记录原因及解除条件，前提变化才重验，不把 blocked 当暂时网络故障反复重试。
- 启动结果不明：沿用现有 recover/查询及派发身份，先确认是否已启动，避免重复 start。
- 明确可重试的临时故障：使用平台支持的有界重试/退避；错误类别和重试依据可追溯，不设置无条件循环。
- 后台构建/测试：优先由工具完成通知或脚本等待；模型收到最终退出码、统计和首个有效错误，需要时再展开日志。没有通知时使用有界状态检查，不反复拉取无变化全文；等待期间只推进真正独立的工作。
- 测试临时文件：优先使用系统临时目录或项目约定的可清理区域。能证明的测试瞬时产物与真实越界分别报告，生产者结束后复查；来源不明仍按现有规则处理，不新增宽泛忽略来隐藏越界。

### 6. 分开保全、合入、技术验收与结案

上述四项分别报告，不能互相推导。“已合入”必须注明目标分支和提交；“技术验收通过”必须绑定被检候选和适用环境；“结案”仍取决于交付范围及有效证据。

首选增加或明确独立快照保全操作：保存候选、补丁及需要的本地材料，记录原任务和未完成项，不要求先通过构建，也不调用 finish 或把 P4 写成通过。保全后仍需核对恢复可用性，才能迁移/退役旧工作区。

用户说“全部合并/收拢”且目标含糊时，在 Git 写入前一次说明并确认要保全快照、迁移执行现场还是技术交付；已有明确授权直接沿用，不重复确认。普通的技术合入仍走现行门禁。

允许未验收候选收拢到某个开发分支属于独立的可选能力，需明确项目规则、目标和授权，保留失败/未验证证据，禁止据此发布或结案；不静默把它接到现有 finish。建议首批只完善独立保全与意图判断，待真实需要时再实施未验收收拢入口。

### 7. 分批实施及回归范围

| 批次 | 具体改动 | 交付与停止条件 |
| --- | --- | --- |
| 第一批：入口与派发减负 | 同步宿主 SKILL、P0/P1/P2、context-handoff、tool-integration、model-routing 和相关模板；精简 runtime 公共包装及 DSH 提示，按已派发执行角色提供必要材料；保持现有回调生命周期 | 状态查询不选模/重规划，工单可覆盖连续步骤，执行者不再重复登记和调查；角色与分支语义统一。只完成这批批准范围，不顺带重写调度器 |
| 第二批：窄输出与项目维护 | 为状态/模型/运行态增加兼容的窄视图，接入事实失效规则、失败分类及等待适配；实现有冲突检查的项目级配置维护；补明确快照保全动作 | 既有完整 JSON 和门禁不退化；不扩大业务 scope；相同前提不重试；保全可恢复但不会生成验收通过或结案事实 |
| 第三批：真实复验与按需扩展 | 在可获得的原项目或等价环境复验；再决定是否补未验收收拢、无 worktree 自动结案或更多平台适配 | 分别报告静态/脚本/真实平台证据；未完成业务继续原计划。没有实际需要不追加同批多集成目标、全新缓存服务或另一套调度层 |

直接联动仍为 devflow、worktree、autopilot 三个技能。外部 Orca/编排与 planning-with-files 先调整组合使用和版本兼容；本批没有证据要求改它们的源码。skill-evolution 和其他业务技能无需因本方案扩大实施范围。

有行为变化时针对实际风险扩展既有 tests/worktree.test.cjs、autopilot-runner.test.cjs、model-config.test.cjs、context-decision.test.cjs 及对应 DSH 适配测试；覆盖输出兼容、重复派发、失效重验和权限冲突。单纯提示词/文档修正做引用与语义核查，不堆砌只匹配实现文字的测试。

### 8. 对照验收与度量

使用相同输入与结果要求验证：二次查询合入状态不重跑构建；模型来源不变不反复查询/确认；全局配置不进入业务 scope；参数错误先修输入；运行中任务不被重复启动；两个独立写任务遇到分支前移或权限冲突仍执行原门禁；快照保全与技术交付输出不同状态。

以工具回传字节、重复读取次数、确认轮数、派发/换窗次数、首次有效产出耗时和最终交付质量对照，平台提供真实 usage 时再记录输入/输出及缓存 token。可以在固定夹具上把“回传字节至少减半”作为试验目标，同时要求输出完整性和质量门禁不退化；不承诺任务产出达到某个固定 token 比例。

## 用户评审与本批完成范围

已按用户要求综合最新反馈，完成分支无关职责、关联技能、意图入口与重复交互的统一方案及分批验收设计。技能实现仍待明确实施范围；本轮未修改技能源码、安装副本、用户已暂存的新反馈或业务配置，未操作 SmartKnora 工作区。

验证级别：仓库规则与部分实现静态检查；文档引用存在性检查。不构成真实 DSH/Orca 接续、工作区迁移或 token 节省复验。
