## 已确认的现象与原因

用户估计实际工作产出约占 10%。本次能确认重复操作及返工确实存在，未取得按步骤分类的 token 计量，不能把 10% 当成实测，也不能推出另外 90% 都是浪费。必要的源码阅读、权限确认和有效测试同样是产出的一部分。

1. **同一事实重复读，且回传太宽。** worktree 状态多次返回完整 scope；为处理一份模型表读取了 917 行计划的前 120 行；编辑提示词时把整份 before/after 回传，合并时为少量语义改动输出了大段行尾差异。工具可以在本地处理完整结果，不需要把全部结果放进模型上下文。这主要是执行失误；技能虽已有“按需读取”和接续摘要，却缺少对同窗重读条件与工具输出的明确默认。
2. **工具重试和等待不断消耗交互。** 相同参数错误连续重试；模型路由查询在配置来源未变时多轮返回同一结果；合并验证期间多次拉取仍在运行的任务输出。失败分类、配置来源区分和完成通知，本来可以替代这些循环。重试本身不是 Devflow 要求。
3. **轻量事项被业务任务的 worktree 流程放大。** 项目模型表写入知识库任务 worktree，需要扩大持权，之后又迁回 master、撤销持权并关闭旧页面。用户明确要项目级统一配置。两个 worktree 当时都没有 master 未包含的提交，只有一个有未提交业务改动；不能证明 worktree 从未有用，但本批没有观察到两条独立交付线。问题在于把已启用等同于每件事都适用，以及未先判断配置所有者。
4. **选模与合入两处决策没有一次说明白。** 局部子智能体查询误当成完整项目目录，表单只列 Sol，反复查询仍没有补足配置。另一次“先把所有内容合并到 master”可能指收拢开发快照，但执行按技术验收门禁推进，直到构建失败才提出这一关键区别。候选 9457de2 已保存，隔离回归 78 项通过，Admin 构建失败，master 未快进。构建失败本身不是无效开销；问题是入口没有明确动作的目标与门禁。

## 建议与可观测验收

- **P0：按任务意图选择最小流程。** 在技能入口先区分状态查询、只读诊断、项目级文档/配置、既有任务接续、正式新任务和技术交付。只有实际需要新的模型路由才进入相应选择；项目级配置从权威根目录读取并维护。状态查询应只核实当前结果，不重新加载历史计划或触发模型选择。小文档任务不得自动扩大业务 scope；并行写入、交付独立且需要隔离时才使用 worktree。
- **P0：同窗复用已核实事实，默认返回摘要。** 在上下文/接续指南明确复用 task-id、cwd、HEAD、持权、用户授权和模型来源；当 HEAD、配置、持权或用户要求变化，或上下文已丢失时，只重验受影响部分。工具默认输出任务身份、状态、冲突/阻断、下一动作、证据路径；需要时才展开 scope 或日志。已有接续摘要优先于全文读取；不能以摘要替代门禁或独立复核。
- **P1：抑制无变化重试，把等待交给工具。** 参数错误先修正输入；相同失败且前提未变，不重复试。对后台测试使用完成通知，模型只收集最终退出码、断言统计和首个有效错误；期间并行做真正独立的工作。测试自己的临时文件不得混进 scope 检查，检查结果应说明看到的是瞬时产物还是实际越界。
- **P1：只问会改变结果的决策。** 模型选择以生效模型表为准，无表就一次给出初始化或引用现有表的选择；不得用局部发现结果造菜单。Git 流程分别报告“已保全”“已合入”“已技术验收”“已结案”；如果项目需要允许未验收快照收拢，应定义显式授权、保留失败证据、不得部署/结案的独立操作，不静默放行门禁。

复验场景：① 同一窗口二次查询合入状态，只做一次窄 Git 读取，不重跑构建；② 已启用 worktree 的项目维护全局模型表，不修改业务 scope、不为只读协作开分支；③ 工具参数报错或产出阻断状态后，前提不变时不重复调用；④ 两个独立任务并发写、分支前移或权限冲突时，仍执行原隔离与组合门禁；⑤ 收拢快照与技术交付走不同出口，失败和未验证项保留。

复验方法：对上述同输入场景做新旧流程对照。平台能提供计量时记录输入/输出和缓存 token；否则只报告工具回传字节、读取次数、重复读取次数、用户确认轮数、首次有效产出耗时与最终交付结果。可先以“工具回传字节至少减半、同窗无状态变化不重读或重复确认”为试验目标，不承诺固定产出比例。通过标准同时要求现有安全与质量门禁不退化，不能用更短的输出掩盖未完成结果。
