## 3. 必要条件：技能、容器、项目环境分别核验

### 3.1 技能与协议

1. 明确区分“安装扩展”“enabled 配置”“控制器真实运行”“新会话接管完成”。前三项不能代替最后一项。
2. 支持主动交接：以独立可验收短目标、阶段检查点或配置预算为触发，不要求等上下文溢出；用户要求试验时立即用两个短工单验证。
3. 第一执行者保存有效证据和下一工单，再 yield；yield 是其最后一次项目写入。下一执行者必须使用不同真实 session/owner/dispatch，核对 cwd、HEAD、快照及交接回执，takeover 后才写入。
4. 新会话依靠有界工单和落盘证据恢复，不回灌全部旧对话。阶段尚有剩余用 yield，整个阶段确实达标才 complete。
5. 对启动未知只 query，不重复 start；心跳过期、同名 owner、消息已投递不等于旧执行者已停止。
6. 读回执是执行者职责。启动接受、ready、turn done、工作区状态和最终业务完成分别核实。提醒机制未实际触发时，不能口头承诺已监听。

### 3.2 容器／执行平台

1. Orca 已运行，CLI 能连接同一运行时；先加载该二进制的版本匹配指南并核对支持的命令。
2. 目标代理已安装且能够真实推理。本次 Orca installed 列出默认 Codex，并完成真实双会话执行；不推论其他模型或厂家已验证。
3. 平台可按真实 cwd 创建独立会话，返回可查询的 session 身份；桥能够以 dispatch_id 保存启动记录并查询。
4. 必须有进程外 controller 持续负责后续派发。模型会话返回 final 不会自行维持轮换；只启动单个工作者不构成完整调度。
5. controller 生命周期和输出必须可观测、可收取。本次由托管后台 job 执行，job_output 收到最终 exit 0；不依赖 DSH 根会话保留业务对话来决定下一派发。
6. 当前平台入口有限制时检查该路径的确切错误，不冒用别人的终端身份；存在可授权替代入口时继续验证。

### 3.3 项目环境

1. 已授权的隔离范围包含真正的主检出、任务目录和控制状态目录；Git common-dir 可能使主检出与当前 worktree 不同，启动前必须解析并显示，不能靠目录名猜测。
2. 使用原唯一任务计划与正式登记入口；任务处于可领取状态，无其他活动写入者。生产迁移先解决原持权，不直接删除 window 或抢占。
3. 对本次实现，配置 execution.enabled=true、adapter=command、require_units=true，command 指向实际 node 与 Orca bridge；这三个开关不是所有平台自动化的唯一可行方式，而是本次成功路径的必要组合。
4. Git 运行态按 runner 要求忽略且未跟踪；工单文件必须存在，任务登记与阶段初始化成功，不能把目录传作 --unit 的 JSON 文件。
5. 工单 task-id、输入路径、write_scope、record_dir 基准一致。输入/写范围相对项目 cwd；回调 --evidence/--next-unit 相对 record_dir。
6. Orca 已知且能访问 runner 选中的实际工作区；技能路径、node 路径和桥脚本须核验。绝对路径含空格按字面参数传递，不拼接 eval。
7. 实际生产路由应明确并保留用户选择，不静默换模型。本实验未证明项目 mixed 各渠道及强度均可用。

## 5. 实际失败点及改进要求

- 发送端身份：从当前 DSH 调用封装的 supervise=true 启动返回 no_active_sender_terminal。普通独立启动成功，Orca 内部 orchestration 也成功。不能推广为 Orca 不支持监督，也不能冒用其他 pane 的 handle。
- 回执读取：执行者数次仅报告“启动成功/等待通知”就结束，用户提醒后才读结果。应区分平台通知能力与执行者实际收割行为；未收到事件要查询权威状态并遵从具体入口的收取协议。真正 orchestration 使用事件唤醒，不写会吞信的 mailbox polling；controller 本身的受控状态循环与托管 job_output 收割是另一层。
- 交接范围：初执行者给自己设定仅当前 worktree，runner 却解析至隔离主检出，导致停在 ready。应在派发前给出已核实的完整隔离范围；普通实验内部目录恢复不应反复让用户确认。对真正范围外业务写仍须保留边界。
- 准备不算执行：重启后只剩 ready/attempts=0，没有 window/dispatch/session；应明确“尚未执行”，核实无旧实例后继续已授权任务，不把计划文件当成功结果。
- 路径与参数：恢复记录包含 task-id 20261125 与 261125 混用、输入路径不一致及 --unit 误传目录。成功链使用主检出内一致的 261125 任务及 JSON 工单。启动前校验，不自动新建第二份同目标计划。
- 技能路径：成功前将实验 command.args 从 .codex/skills 指向本轮已加载的 .agents/skills 实际安装位置。旧路径读取遇到 reparse/no-follow 拒绝；未核实旧链接目标，不能声称旧脚本不存在或该路径就是唯一失败根因。
- shell：先前 PowerShell 的 $_ 在双引号 Bash 中被展开，产生错误且命令仍 exit 0。后改用正确传参/EncodedCommand；检查 stdout/stderr 与语义结果，不能只看 exit 0。复杂脚本优先文件传参。
- 短时锁：成功运行中 controller 输出 AXNS_COORDINATION_BUSY，随后自动继续并完成。该信号不直接等于失败或需要用户处理，不得为了通过删除锁。

### 公共协议与平台适配分层

公共流程依赖可靠的新会话创建、状态查询、执行权交接和结果回收能力，不强制所有项目安装 Orca 或 DSH。Orca 是本次实际通过的实现；Multica 和其他平台必须通过同等真实验收才能替换。项目选择 Orca 路径时，Orca 及其桥/控制器属于这条路径的运行依赖，不能只在提示词末尾提及。

### 需要落实的流程闭环

1. **接入阶段**：一次性确认所选平台/CLI/代理/模型、实际主检出与任务目录、登记与锁状态、桥和控制器、结果收取通道，并完成隔离双工单验证。缺口由 AI 在授权内处理，不将普通初始化或阶段切换反复交给用户操作。涉及未授权平台安装、渠道变更或外部操作时单独说明实际缺口。
2. **职责划分**：主协调者负责总体目标、依赖、工单边界、质量门禁及集成；进程外控制器负责启动、查询和轮换，不判断业务成功；工作者执行当前工单、保存证据与下一工单并回调。业务后续派发不能只靠原模型会话一直在线记住下一步。
3. **正常主动交接**：按可验收工单或阶段检查点触发，补以步骤/时间/可观测上下文预算；不等上下文耗尽，不按每条命令制造会话。正常轮换不暂停整体目标，不因换窗另建业务任务/worktree。
4. **执行权与身份**：旧执行者收拢子任务与后台写入、保存检查点后交权；新执行者验证 task-id/cwd/分支/HEAD/工作区快照和前次回执，使用不同 session/owner/dispatch 接管。是否已停写与 OS 进程退出分别取证；本例未证明所有外部进程静止，不能外推。
5. **结果收取**：启动前明确通知送到哪个协调者、谁读取完成回执、通知未送达如何查询、有限控制器结束后由谁继续。事件订阅可用不等于当前会话已经订阅；启动后不能无监督结束并要求用户再提醒。遵从具体平台的事件/邮箱协议，不用会吞信的轮询代替事件接收。
6. **中断恢复**：Orca 重启、控制器结束、模型异常、回执丢失分别处理；从现有持久派发查询，不重复 start、不删持权、不清 attempts。确认旧执行停止并保存依据后续接；控制器上限是正常边界，应明确报告是否仍有未完工单，而非悄然停止或声明任务完成。
7. **状态统一**：业务计划与证据保持唯一入口；平台会话状态、controller 状态、工单状态、业务阶段验收分别维护并能关联。done/exit 0 不代替业务验收；工作区卡片 in-progress 也不推翻真实 complete 回执。
8. **生产迁移**：实验通过后核实原任务实际执行者、子树与未提交工作，保留既有授权和唯一任务身份。配置仅影响后续合法派发，不能用改 adapter 自动接管当前窗口。对有活动写入的任务先完成正式交权。
