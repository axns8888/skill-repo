本次对照以项目现行规范、初始化实际产物和阶段指令为依据。未逐文件审计用户提到的其他项目生成代码，因此下面区分“技能中已确认的缺口”和“这些缺口可能导致的产出问题”，不把原因推断冒充现场复现。

## 判断

旧技能对流程组织和验证证据规定较明确，但没有为新项目提供同等明确的工程基线。入口把技术栈、架构、界面与发布约定整体交给项目维护；初始化生成的项目基线主要是待填写字段，没有随技能落位的架构、编码与 UI 专题规范。复核强调行为和证据，但未明确注释、命名、源码落位、UI 一致性的适用检查与放行条件。

这使快速创建项目存在一个空档：没有现成规范可沿用时，执行者可以生成流程目录并进入编码，却没有确定业务源码如何组织、名词如何统一、哪里应有注释、页面如何保持一致，以及本期系统如何算完成。用户反馈的平铺、随意命名、缺注释与 UI 规范薄弱，与这一缺口相符。

## 已落地的修改

- 新增 `references/engineering-standards.md`：工程准备的出口、规范所有权、最低要求、模块完成矩阵和阶段检查。
- 新增三个随技能携带的模板：`assets/architecture-baseline.md`、`coding-baseline.md`、`ui-baseline.md`。它们含通用底线及待项目具体化的决定，不依赖仓库外可选模板。
- 初始化增加 `_plan/prompts/architecture.md`、`coding.md`、`ui.md` 以及 `_plan/guides/engineering-standards.md`；更新项目基线、README、flow 和导航引用。
- 将规范接入 SKILL 入口、工作流、阶段提示词及 P2/P3 窗口。新系统先具体化规范再写对应业务代码；只初始化文档不代表完成工程准备。
- 在质量门禁和任务记录中增加源码结构、命名/引用、关键注释、UI 和真实业务闭环检查。本轮新增违例修正前不能放行；人工验收开关不控制技术门禁。
- 保留已有流程授权、轻量记录和扩展协议。小改动可简记，不能据此免除本次适用的工程要求。

没有把 TK-Worker 的 Python/Vue/Tauri、Koi 组件、固定目录名、领域短名映射、数据库主键、删除历史兼容层或特定数据政策设成所有项目的通用要求。具体项目仍需确定自己的技术和业务契约。

## 旧项目采用方式与验证边界

初始化继续只补缺失文件，已有规范逐字保留。已有项目使用当前任务有界合并新增规则，并在现行基线建立唯一入口；重跑脚本不会自动升级旧的阶段文档。没有改写 TK-Worker 或其他业务项目。

自动检查验证初始化的文件落位、独立分发、链接、重复执行、旧项目规范保留、预检失败和参数行为；它们不能证明模型在任意新系统中必然正确组织源码。工程行为仍应在实际开发中通过真实模块和交付门禁观察，不能以模板或测试文件存在代替产出质量。
